# Plan för story 002 — LiteDB → SQLite med EF Core

Förutsätter att story 001 är mergad (net10.0, EF Core 10).

## Ansats
`DishService` behåller sitt gränssnitt `IDishService` exakt som idag — alla komponenter
(`PreviousDishes.razor`, `DayCard`, `ImageFromDbComponent`, …) är då oförändrade utom där
nyckeltypen syns. Bytet sker under ytan: `ILiteDbService` → `AppDbContext`.

Migreringen är en engångskörning som startas via ett kommandoradsargument i den befintliga
appen. Inget extra projekt: LiteDB-paketet finns ändå kvar tills migreringen är körd, och
ett eget projekt skulle kräva delad entitetskod eller duplicering.

### Beslut 1 — nyckeltyp: `Guid`
`ObjectId` försvinner. Inget utanför appen refererar till id:t (inga URL:er, ingen export),
så nya `Guid`-nycklar kan genereras vid migreringen. Ingen `LegacyId` sparas — den skulle
inte användas av något.
`IDishService.GetImageFromDbAsync(string imgId)` behåller `string` som parametertyp
(bild-id är redan en `Guid.ToString()` idag) så `ImageFromDbComponent` inte behöver röras.

### Beslut 2 — `Ingredients`: JSON-kolumn via värdekonverterare
Ingredienser läses och skrivs alltid som hel lista tillsammans med sin rätt; ingen vy söker
eller filtrerar på enskild ingrediens. En egen tabell hade gett en join utan nytta.
Konverterare + `ValueComparer` (annars upptäcker EF Core inte ändringar i listan).

### Beslut 3 — bilder: egen tabell `DishImages` med `byte[] Content`
Valet står mellan BLOB och filer på disk. **BLOB vinner**, men i en egen tabell, inte som
kolumn på `Dish`:
- *Varför BLOB och inte disk:* en fil att backa upp, en volym (`/app/data`), och migreringen
  blir allt-eller-inget i en transaktion. Filer på disk innebär två artefakter som kan hamna
  ur synk vid rollback — och storyn kräver uttryckligen att rollback till LiteDB fungerar.
  Databasen växer, men datamängden är en bild per rätt i en privat app.
- *Varför egen tabell:* med BLOB direkt på `Dish` skulle listvyns `GetAllDishes` dra med sig
  varje bild i varje sidhämtning. Egen tabell + separat query i `GetImageFromDbAsync` gör att
  listan inte blir långsammare (UX-kriteriet om laddning).

`DishImage`: `Id` (Guid, PK), `FileName` (string, motsvarar dagens `CreateSafeImageTitle`),
`Content` (byte[]). Ingen FK till `Dish` — kopplingen är `Dish.ImageId` precis som idag.

## Datamodell
```
Dish        Id Guid PK, Title, Notes, ImgUrl?, RecipeUrl?,
            Ingredients (JSON text), Rating int, When DateTimeOffset, ImageId Guid?
DishImage   Id Guid PK, FileName string, Content byte[]
```

## Berörda filer/moduler
- `WhatToEatApp.csproj` — `Microsoft.EntityFrameworkCore.Sqlite` + `.Design`. LiteDB behålls
  (används av migreringsverktyget).
- `Data/AppDbContext.cs` (ny) — `DbSet<Dish>`, `DbSet<DishImage>`, konverterare för `Ingredients`.
- `Entities/Dish.cs` — `ObjectId DishId` → `Guid Id`; konstruktorerna följer med. `UpdateDish` orört.
- `Entities/DishImage.cs` (ny).
- `Services/Dish/DishDto.cs` — `ObjectId? DishId` → `Guid DishId`; mappningarna oförändrade i övrigt.
- `Services/Dish/DishService.cs` — skrivs om mot `AppDbContext`. Samma metodsignaturer,
  samma sortering (`OrderByDescending(Rating)`), samma paginering, samma `GetTodaysDish`-logik.
- `Services/Persistance/LiteDbService.cs` — flyttas till migreringsverktyget, tas bort ur DI.
- `Shared/PreviousDish/PreviousDishEventArgs.cs` — `ObjectId DishId` → `Guid DishId`.
- `Shared/Ingredients/IngredientsComponent.razor` — `DishId!.ToString()` fungerar på Guid;
  `!` tas bort eftersom Guid inte är nullable.
- `Pages/PreviousDishes.razor` — `x.DishId == e.DishId` fungerar oförändrat på Guid.
- `Migration/LiteDbToSqliteMigrator.cs` (ny) + gren i `Program.cs`.
- `appsettings.json` — `SqliteConnection: "Data Source=/app/data/whattoeat.sqlite"`.
  `LiteDbConnection` behålls så länge migreringsverktyget finns kvar.
- `Program.cs` — `AddDbContext<AppDbContext>`, `AddLiteDbService` bort, migreringsgren.

## Migreringsverktyget
`dotnet WhatToEatApp.dll --migrate-litedb <källa.db> <mål.sqlite>`

- Öppnar LiteDB-filen **read-only** (`Connection=shared;ReadOnly=true`) — kravet att
  originalfilen aldrig rörs.
- Skapar SQLite-schemat via `Database.Migrate()`, läser alla `dishes` + alla filer i
  `wteImages`/`wteChunks`, skriver i **en** transaktion. Vid fel: rollback, felutskrift
  med vilken rätt som fallerade, exit-kod ≠ 0, ingenting skrivet.
- `ObjectId` → ny `Guid` per rätt; bildernas id är redan Guid-strängar och behålls, så
  `Dish.ImageId` fortsätter peka rätt.
- Utskriften följer storyns wireframe exakt.

## Felhantering vid start
Saknad eller oöppningsbar databasfil ska ge ett begripligt svenskt meddelande, inte en vit
sida: fånga vid start/första query och visa via befintlig `/Error`-sida. Ingen ny felvy byggs.

## Ordning
1. Paket + `AppDbContext` + entiteter + EF-migration → verifiera: `dotnet ef migrations add Initial`
   och bygget grönt.
2. Skriv om `DishService` mot EF Core, byt nyckeltyp genom DTO/EventArgs/komponenter →
   verifiera: bygget grönt, appen startar mot tom SQLite-fil och visar tomtillståndsvyn.
3. Migreringsverktyget → verifiera: körd mot en **kopia** av produktionsfilen, utskriften
   visar samma antal rätter och bilder som LiteDB-filen innehåller, originalfilen har
   oförändrad mtime/checksumma.
4. Före/efter-jämförelse: lista (antal, ordning, titlar, betyg, ingredienser, datum),
   en rätt med bild, "Dagens rätt" för samma veckodag → verifiera: storyns acceptanskriterier.
5. CRUD-genomgång: lägg till, redigera med utbytt bild (gammal bild ska försvinna ur
   `DishImages`), ta bort → verifiera: samma beteende som före.
6. Rensa: inga `using LiteDB` kvar utanför `Migration/`.

## Noteringar
- **Befintlig bugg som inte fixas här:** `AddDishAsync` sätter `newDish.ImageId` men infogar
  sedan `dishDto.MapToNewDish()` på nytt — bilden tappas vid nyskapande. Att skriva om
  metoden mot EF Core gör felet uppenbart. Jag föreslår en egen story; att tyst "fixa" det
  bryter mot kriteriet "fungerar som tidigare". Coder: behåll beteendet, flagga i PR:en.
- `DateTimeOffset` lagras av SQLite-providern som text och sorteras korrekt — ingen
  specialhantering behövs.
- Docker-volymen är redan `/app/data`; båda filerna ligger där under övergången.

## Avgränsningar
- LiteDB-filen raderas inte, och LiteDB-paketet tas inte bort (rollback ska fungera).
- Ingen ny funktionalitet, ingen UI-förändring, ingen omdesign av datamodellen utöver bytet.
- Ingen automatisk migrering vid appstart — körningen är manuell och medveten.
- Inga index utöver primärnycklarna; datamängden motiverar det inte.
