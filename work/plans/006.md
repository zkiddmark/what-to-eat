# Plan för story 006 — egen inloggning, Firebase bort

## Den avgörande begränsningen
En cookie sätts på ett HTTP-svar. En Blazor Server-komponent kör över en SignalR-krets där
svaret för länge sedan är skickat — `HttpContext.SignInAsync` går **inte** att anropa från
`Login.razor`. Det är därför dagens lösning hamnade i JavaScript från början.

Lösningen: låt inloggning, registrering och utloggning vara **Razor Pages**, inte Blazor.
Appen har redan `AddRazorPages()` och `Pages/_Host.cshtml`, så ingen ny infrastruktur
tillkommer. Dessa sidor äger en riktig `HttpContext`, sätter cookien och redirectar.
Resten av appen förblir Blazor och läser den inloggade användaren ur kretsens `HttpContext`
via den inbyggda `ServerAuthenticationStateProvider` som `AddServerSideBlazor()` redan
registrerar. `FirebaseAuthStateProvider` raderas utan ersättning.

Detta är också vad som uppfyller kriteriet *"kontrollen sitter på servern, inte bara i vyn"*:
`UseAuthentication`/`UseAuthorization` i pipelinen, inte en komponent som gömmer markup.

## Val av teknik

**Lösenordshash: `PasswordHasher<AppUser>` ur `Microsoft.Extensions.Identity.Core`.**
PBKDF2-HMAC-SHA512, 210 000 iterationer, slumpat salt per lösenord, versionsprefix i hashen
så arbetsfaktorn kan höjas senare utan att gamla hashar slutar fungera. Förstapartspaket,
inget tredjepartsberoende. Argon2id vore starkare men kräver ett externt paket för en app
med en handfull användare — bedömningen är att det inte bär sin vikt. Säg till om du vill
ha bcrypt/Argon2 i stället, det är ett litet byte.

**Inte full ASP.NET Core Identity.** Identity drar in sju tabeller, scaffoldad UI och ett
rollsystem vi inte använder som det är tänkt. Storyn behöver fem fält. Vi tar `PasswordHasher`
ur Identity och lämnar resten — betydligt mindre kod att äga.

**Cookie: `AddAuthentication().AddCookie()`** med `HttpOnly = true`, `SecurePolicy = Always`,
`SameSite = Lax` (måste vara Lax, inte Strict, annars saknas cookien vid redirect tillbaka
från inloggningssidan), `SlidingExpiration`, och `LoginPath = "/login"`.

**Utloggning gör sessionen obrukbar:** cookie-auth är självbärande, så det räcker inte att
radera kakan hos klienten — en kopia skulle fortsatt gälla. Varje användare får en
`SecurityStamp` (Guid) som ligger som claim i cookien och roteras vid utloggning och vid
lösenordsbyte. `OnValidatePrincipal` jämför claimen mot databasen och avvisar vid skillnad.
Det är den mekanism kriteriet faktiskt kräver.

## Datamodell
```
AppUser   Id Guid PK
          Alias string
          Email string          (unikt index, normaliserat till gemener)
          PasswordHash string
          Status enum           Pending | Approved | Rejected   (int i databasen)
          Role string           "admin" | "user"   (sätts i 007, default "user")
          SecurityStamp Guid
          CreatedAt DateTimeOffset
          FailedAttempts int
          LockedUntil DateTimeOffset?
```
`Role` läggs till redan här med default `"user"` — kolumnen kostar ingenting och slipper en
extra migration i 007. Ingen rollogik byggs i denna story.

## Berörda filer/moduler
Nytt:
- `Entities/AppUser.cs`, `Enums/AccountStatus.cs`
- `Data/AppDbContext.cs` — `DbSet<AppUser>`, unikt index på `Email`. Ny EF-migration.
- `Services/Auth/IUserService.cs` + `UserService.cs` — `RegisterAsync`, `ValidateCredentialsAsync`,
  `RotateSecurityStampAsync`. All verifiering här, inget i vyn.
- `Pages/Login.cshtml(.cs)`, `Pages/Register.cshtml(.cs)`, `Pages/Logout.cshtml.cs`
- `Data/UserSeeder.cs` — skapar `peter@stjern.se` som godkänd admin vid start om inga
  användare finns. Lösenordet läses ur konfiguration (`ADMIN_INITIAL_PASSWORD`, env-variabel
  eller user-secrets). Saknas värdet: appen startar men loggar en tydlig varning och seedar
  inte — inget default-lösenord i koden.

Ändrat:
- `Program.cs` — `AddJsonFile("./ExcludedSecrets/...")` bort, `FirebaseOptions` bort,
  Firebase-registreringarna bort; `AddAuthentication`/`AddCookie`, `UseAuthentication`,
  `UseAuthorization`, seeder-anrop.
- `App.razor` — `OnAfterRenderAsync`/`InitializeFirebase` bort; `NotAuthorized` visar en
  hänvisning i stället för att navigera under rendering (dagens `RedirectToLogin()` i
  markup är en bieffekt mitt i renderingen). Cookie-pipelinens `LoginPath` gör omdirigeringen.
- `Shared/NavMenu.razor` eller `MainLayout.razor` — visa alias + utloggningslänk.
- `Pages/_Host.cshtml` — ta bort ev. Firebase-script.
- `WhatToEatApp.csproj` — `Microsoft.Extensions.Identity.Core`.

Raderat: `Auth/FirebaseService.cs`, `Auth/FirebaseAuthStateProvider.cs`,
`wwwroot/js/firebaseAuth.js`, `Pages/Login.razor`, `ExcludedSecrets`-beroendet.

## Hur säkerhetskriterierna uppfylls
- *Samma svar och samma tid oavsett om e-posten finns:* hittas ingen användare körs ändå
  `VerifyHashedPassword` mot en förberäknad dummy-hash, sedan returneras samma fel. Utan det
  avslöjar svarstiden vilka adresser som finns.
- *Konto som väntar på godkännande:* statusen kontrolleras **efter** lösenordsverifieringen.
  Annars blir väntlägesmeddelandet i sig en kontokartläggning. Storyn vill att användaren får
  veta — det är rätt, men bara för den som bevisat att lösenordet stämmer.
- *Bromsa upprepade försök:* `FailedAttempts` räknas upp, vid 5 sätts `LockedUntil` till
  +15 minuter. Nollställs vid lyckad inloggning. Spärren gäller kontot, och meddelandet är
  samma generiska som vid fel lösenord.
- *Lösenordspolicy:* minst 12 tecken, ingen övre gräns under 256, inga teckenklasskrav.
- *Antiforgery:* Razor Pages-formulären använder ramverkets inbyggda token.

## Ordning
1. Entitet, `DbContext`, migration, `UserService` med hashning → verifiera: bygget grönt,
   migrationen skapar tabellen, ett testkonto kan skapas och verifieras i ett enhetstest
   eller via seedern.
2. Cookie-auth i pipelinen + `SecurityStamp`-validering → verifiera: en handgjord begäran mot
   `/` utan cookie omdirigeras till `/login`.
3. Razor Pages för login/register/logout + svensk copy enligt wireframe → verifiera:
   registrering ger bekräftelsevyn, inloggning med väntande konto nekas med rätt besked.
4. Riv ut Firebase i en egen commit → verifiera: `grep -ri firebase` ger inga träffar i kod,
   konfiguration eller `wwwroot`; appen startar utan `ExcludedSecrets`.
5. Seeda admin ur env-variabel → verifiera: tom databas + satt variabel ger inloggningsbar admin.
6. Utloggning → verifiera: spara cookievärdet före utloggning, spela upp det efteråt med
   curl → nekas.
7. Öppna listan som inloggad → verifiera: de 31 recepten är oförändrade.

## Noteringar
- **Detta är en säkerhetsfix, inte bara en refaktorering.** Tills 006 är driftsatt kan vem som
  helst med en webbläsarkonsol göra sig till inloggad användare. Värt att prioritera före 007–009.
- `_Imports.razor` har `@attribute [Authorize]` globalt. Det fortsätter gälla och blir nu
  verkningsfullt; `Login`/`Register` ligger utanför Blazor och berörs inte av det.
- Att appen inte gick att köra lokalt utan `ExcludedSecrets` försvinner som problem — därmed
  blir bildflödet i story 003 klickbart igen.

## Avgränsningar
- Ingen e-post, inget "glömt lösenord", ingen tvåfaktor, ingen bekräftelselänk.
- Ingen rollogik och ingen godkännandevy — det är 007. Fram till dess godkänns konton med
  en `UPDATE` i databasen.
- Inga andra vyer översätts till svenska.
