# Plan för story 008 — ägarskap av recept

## Ansats
`Dish` får `OwnerId` (FK → `AppUser`). Behörighetskontrollen läggs i `DishService`, i samma
metoder som utför ändringen — `UpdateDishAsync` och `DeleteDishAsync`. Det är vad kriteriet
*"i det lager som utför ändringen"* kräver: ett handgjort anrop med ett giltigt recept-id
går genom samma metod och nekas där.

Vem som är inloggad hämtas av tjänsten själv via `AuthenticationStateProvider`. `OwnerId`
sätts i `AddDishAsync` från den källan och läses **aldrig** ur `DishDto` — därför får DTO:n
ett läsbart `OwnerAlias` för visning, men inget skrivbart `OwnerId`. Kommer det ändå in ett
ägarvärde från klienten ignoreras det, eftersom fältet inte finns.

**`DishService` måste bli `Scoped`.** Den är `Transient` idag; `AuthenticationStateProvider`
är scoped per krets, och att injicera scoped i transient fungerar här men gör livstiderna
otydliga. `Scoped` matchar kretsen och är rätt livstid när tjänsten bär ett användarberoende.

## Datamodell
```
Dish.OwnerId  Guid  FK -> AppUser.Id, ON DELETE RESTRICT
```
`RESTRICT`, inte kaskad: att avslå eller ta bort en användare ska inte tyst radera deras
recept. Index på `OwnerId` för listvyns join mot alias.

EF-migrationen sätter `OwnerId` för samtliga befintliga rätter till `peter@stjern.se`:s id
i samma migration som kolumnen skapas, med ett `UPDATE` i `Up()` som slår upp id:t på
e-postadressen. Kolumnen kan därför vara `NOT NULL` direkt — inga nullbara ägare att hantera
i koden. Finns ingen sådan användare avbryts migrationen med ett tydligt fel hellre än att
lämna halvdan data.

## Berörda filer/moduler
- `Entities/Dish.cs` — `OwnerId`. `UpdateDish` ska **inte** kopiera över `OwnerId`; ägaren
  byts aldrig via en uppdatering.
- `Data/AppDbContext.cs` — relation, index. Ny migration med datauppdateringen.
- `Services/Dish/DishDto.cs` — `OwnerAlias` (läsbart), ev. `CanEdit` för vyn.
- `Services/Dish/DishService.cs`
  - `AddDishAsync`: sätter `OwnerId` från inloggad användare.
  - `UpdateDishAsync`/`DeleteDishAsync`: nekar om inloggad varken är ägare eller admin.
  - `GetAllDishes`/`GetTodaysDish`: joinar in ägarens alias och beräknar `CanEdit`.
    Sorteringen från story 004 behålls oförändrad.
- `Shared/PreviousDish/PreviousDishComponent.razor` — ägarraden under titeln, knappar
  villkorade på `CanEdit`.
- `Shared/Day/DayCard.razor` — samma villkor på redigera/ta bort; visar fel enligt 003:s mönster.
- `Program.cs` — `AddTransient<IDishService>` → `AddScoped`.

## Nekad ändring — hur det syns
Tjänsten kastar ett eget `ForbiddenException` (eller returnerar ett resultatobjekt; Coder
väljer, men konsekvent). Vyn fångar det på samma sätt som spar-felet i story 003 och visar
ett begripligt meddelande. Ingen tom sida, ingen stacktrace.

## Ordning
1. Kolumn + migration med datauppdatering → verifiera: kör mot en kopia, alla 31 recept har
   Peters id, ingen rad har null.
2. `OwnerId` sätts vid skapande → verifiera: nytt recept som Alex får Alex som ägare.
3. Kontroller i Update/Delete → verifiera: som Alex, anropa mot Peters recept-id — nekas.
   Testa via tjänsten direkt, inte bara genom vyn; det är kriteriets poäng.
4. Admin redigerar annans recept → verifiera: går igenom.
5. Vyn: ägarrad och villkorade knappar → verifiera: egna recept har knappar, andras inte,
   admin har på alla.
6. Användare utan egna recept → verifiera: ser hela listan, inte en tom vy.

## Noteringar
- `DeleteDishAsync` tar idag emot en `DishDto` och litar på dess `ImageId` för att radera
  bilden. Efter denna story måste den ändå läsa rätten ur databasen för ägarkontrollen —
  låt den använda den lästa raden även för bilden, så att en klient inte kan styra vilken
  bild som raderas genom att skicka ett annat `ImageId`. Liten ändring, samma metod.
- Alla inloggade ser alla recept — ingen filtrering på ägare i listan. Det är uttalat i
  storyn och värt att inte "förbättra".

## Avgränsningar
- Inget överlämnande av ägarskap, inga delade recept, ingen filtrering på ägare.
- Ingen ändring av röstning eller betyg — det är 009.
