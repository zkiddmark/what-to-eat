# Plan för story 007 — roller och godkännande

Bygger på 006. Kolumnen `AppUser.Role` finns redan därifrån; denna story ger den mening.

## Ansats
Rollen läggs som `ClaimTypes.Role` i cookien vid inloggning. Adminvyn är en Blazor-sida med
`@attribute [Authorize(Roles = "admin")]`. I Blazor Server körs komponenten på servern, så
attributet **är** en serverkontroll — men det skyddar bara sidan. Handlingarna (godkänn,
avslå) kontrolleras dessutom i `UserService`, som verifierar anroparens roll innan den
skriver. Utan det räcker det att nå tjänsten på annat sätt för att kringgå vyn.

`UserService` får den inloggade användaren från `AuthenticationStateProvider` — aldrig från
en parameter som anropande kod kan hitta på. Det är vad kriteriet *"kan inte ändra sin egen
roll genom att manipulera det som skickas"* kräver: rollen skickas aldrig med.

## Datamodell
Oförändrad. `Status` (Pending/Approved/Rejected) och `Role` finns från 006.

## Berörda filer/moduler
- `Services/Auth/UserService.cs` — `GetPendingAsync`, `GetUsersAsync`, `ApproveAsync(Guid)`,
  `RejectAsync(Guid)`. Var och en börjar med en rollkontroll mot inloggad användare.
- `Pages/Admin/Users.razor` (ny) — `@page "/admin/anvandare"`, `[Authorize(Roles = "admin")]`.
  Två listor enligt wireframe, laddningstillstånd, tomtillståndstext, låsta knappar under
  pågående handling, felmeddelande per rad.
- `Shared/NavMenu.razor` — länk till adminvyn inuti `<AuthorizeView Roles="admin">`, så en
  vanlig användare inte ser att vyn finns.
- `Shared/ConfirmDialog/` — återanvänds för bekräftelsen vid avslå. Ingen ny dialog byggs.
- `Program.cs` — inget nytt; cookie-auth från 006 bär redan rollclaimen.

## Utelåsningsskydd
`RejectAsync` vägrar om mål-id är samma som inloggad användare. Dessutom vägrar den avslå
den sista kvarvarande godkända adminen — annars kan två administratörer avslå varandra och
låsa appen. Båda kontrollerna sitter i tjänsten, inte i vyn.

## Ordning
1. Rollclaim vid inloggning → verifiera: logga in som admin, `AuthorizeView Roles="admin"`
   visar innehåll; som vanlig användare inte.
2. Tjänstemetoder med rollkontroll → verifiera: anrop som icke-admin kastar/nekas.
3. Adminvyn enligt wireframe → verifiera: väntande konton listas med alias, e-post, datum.
4. Godkänn → verifiera: raden flyttas till användarlistan, och kontot kan logga in direkt.
5. Avslå med bekräftelse → verifiera: kontot kan inte logga in.
6. Skriv `/admin/anvandare` direkt som vanlig användare → verifiera: nekad åtkomst, inte en
   tom sida. Kontrollera även att navigationslänken inte syns.
7. Försök avslå sitt eget konto och sista adminen → verifiera: nekas.

## Noteringar
- Rollen ligger i cookien. Ändras någons roll direkt i databasen slår det inte igenom förrän
  hen loggar in på nytt. Storyn har rolländring via gränssnittet utanför omfattning, så det
  räcker här — men om det byggs senare måste `SecurityStamp` roteras vid rollbyte, precis som
  vid utloggning i 006. Noterat så att det inte glöms.
- Väntande och avslagna konton skiljs åt i databasen men bara väntande visas i den övre
  listan; avslagna hamnar inte i någondera listan. Storyn beskriver inte en vy för dem och
  jag bygger ingen.

## Avgränsningar
- Två roller, inget mer. Ingen rollredigering i gränssnittet.
- Ingen vy för avslagna konton, ingen möjlighet att ångra ett avslag i gränssnittet.
- Inget ägarskap och ingen röstning — 008 och 009.
